Quantization for LLM deployment

Interactive guide to shrinking 16-bit models into 8-, 4-, and even 2-bit formats — and to the three-way tradeoff every deployment actually makes: accuracy you keep, memory you save, and what happens to arithmetic cost and latency. Change a number, inspect the rounding, and test which resource actually limits decoding.

01Fewer bits, the same model shape

A weight is a learned number. An activation is an intermediate result produced while the model runs. Quantization represents selected numbers using fewer bits, plus information needed to interpret them. It does not remove layers or parameters.

Store less

For 70 billion weights, 16-bit payloads occupy 140 GB; 4-bit payloads occupy 35 GB. Scales, zero-points, unquantized tensors, and alignment add to that. KV cache and runtime memory are separate.

Move less

Small-batch dense decoding often streams much of the model each step. Compressed weights reduce that traffic. Batching amortizes weight reads, while long contexts increase attention and KV-cache traffic.

Execute differently

A dense matrix multiply retains its multiply-accumulate count. One multiply plus one addition counts as two operations. Lower-precision kernels may execute them faster; conversion and scaling add work.

Read W4A16 as a recipe. W means weights, A means activations. W4A16 stores 4-bit weights and uses 16-bit activations; many kernels unpack weights into a wider compute type. W8A8 lowers both operand precisions. The accumulator can still be wider. KV precision is an independent choice. [1]
Four times smaller is not automatically four times faster. Dequantization, kernel support, batch size, attention, and device utilization all matter. MoE models have different active and total parameter counts; the calculator below models dense decoders only.

03Separate the format from the method

INT4 and FP8 describe numbers. GPTQ and AWQ describe how weights are transformed. PTQ and QAT describe when quantization is introduced. GGUF describes a container. These categories overlap.

WEIGHT-ONLY · PTQ

GPTQ

Compensate for rounding error

Use calibration activations to approximate sensitivity. Quantize weights sequentially and compensate for their errors in the remaining weights.

Uses approximate second-order information rather than rounding every weight independently. Calibration and kernel compatibility matter. Original source ↗

WEIGHT-ONLY · PTQ

AWQ

Protect important channels

Use activation statistics to identify salient channels. Scale their weights up and inversely scale the corresponding activations before quantization, preserving the unquantized product.

For a channel scale a: W′ = aW and x′ = x/a. This can reduce effective rounding error on salient weights. It does not mean quantizing activations. Original source ↗

FORMAT · ADAPTER TRAINING

NF4 and QLoRA

Use a nonuniform codebook

NF4 allocates 16 levels to suit a normal distribution. QLoRA trains adapters through a frozen quantized base, with higher-precision computation. Double quantization compresses the scales themselves.

QLoRA reports about 0.37 bits per parameter saved by double quantization in its setup. Adapter training is distinct from training all base weights with quantization awareness. Original source ↗

CONTAINER + TENSOR FORMATS

GGUF and K-quants

A file format can contain multiple precisions

GGUF is a model container, not one quantization algorithm. Q4_K is a tensor format with 256-weight super-blocks; Q4_K_M is a model conversion recipe that can mix tensor types.

Effective bits depend on the mixture and metadata. Do not interpret “4” as exactly four stored bits per model parameter. Runtime backends determine the actual arithmetic. Original source ↗

WEIGHTS + ACTIVATIONS · PTQ

SmoothQuant

Move difficulty from activations to weights

Rescale activation channels down and weights up while preserving the original product. This smooths activation outliers so both operands can be quantized to INT8.

Its target differs from AWQ: activation quantization is central here. Native low-precision kernels are needed to realize a compute benefit. Original source ↗

NUMERICAL FORMATS

FP8 and FP4

Keep floating point, use fewer bits

Floating formats have sign, exponent, and fraction fields. Their levels are nonuniform. FP8 E4M3 and E5M2 have different range/precision tradeoffs; scaled FP4 formats such as NVFP4 use block scales.

Finite range still causes clipping or overflow without suitable scaling. FP8 weight payload is half that of FP16; KV quantization is separate. FP4, NF4, and INT4 are not interchangeable. Original source ↗

CACHE · INDEPENDENT OF WEIGHTS

KV-cache quantization

Shrink the growing context state

For full-attention GQA, cache payload = 2 × layers × KV heads × head dimension × cached tokens × batch × bytes per element. Quantizing weights does not automatically quantize this cache.

KIVI uses per-channel key quantization and per-token value quantization, with a higher-precision residual region. Metadata and residuals reduce ideal memory savings. Original source ↗

VECTOR QUANTIZATION

QuIP# and AQLM

Quantize groups of weights jointly

Randomized Hadamard transforms reduce concentration in individual coordinates. Lattice codebooks then represent vectors of weights, with fine-tuning used to recover quality.

Vector methods differ from scalar rounding. Low-bit quality and latency need evaluation with the actual checkpoint, kernels, and task. Original source ↗

AQLM represents each weight vector as a sum of learned codewords and optimizes the codebooks to preserve model behavior. It is another route to vector quantization, rather than a variant of the scalar INT2 grid in this playground. AQLM paper ↗

TRAINING PROCEDURE

Quantization-aware training (QAT)

Learn with simulated quantization

Insert quantize/dequantize operations during training so parameters adapt to rounding and clipping. A straight-through estimator approximates gradients through the quantizer.

QAT does not specify a bit width, activation format, or kernel. A W4A16 QAT checkpoint can still use wider arithmetic at deployment. Original source ↗

Inspect the assumptions and equations

One decode step emits one token per sequence. Batch B shares a weight read, but each sequence has its own KV cache. Devices are assumed to shard weights and KV perfectly; interconnect and collective costs are excluded. The 8% headroom and 0.75 GB runtime allowance per device are placeholders, not measured usage. Model profiles are hypothetical dense GQA/MHA shapes, not checkpoint configurations.

The estimate excludes prefill, allocator fragmentation, kernel efficiency, KV scale metadata, cache writes, and activation workspaces beyond that allowance. “Fits” is an ideal memory budget test, not confirmation that a runtime supports this format or parallel layout. All capacities use decimal GB (10⁹ bytes), not GiB.

05Compare memory, then measure quality

These bars use the calculator’s weights, KV payload, and runtime allowance. Every bar shares the same linear scale. The line marks 92% of the combined device capacity; the remainder is reserved as headroom.

There is no universal “accuracy retained” percentage. Weight RMSE is not task accuracy, and perplexity is not a code or reasoning benchmark. This page computes numerical error in the toy sample; it does not infer model quality from bit width.

Keep the comparison controlled

Use the same base model, evaluation prompts, tokenizer, decoding settings, and context lengths. Keep quantization calibration data separate from held-out evaluation.

Measure the actual task

Report perplexity alongside relevant task scores: code tests, exact-match answers, retrieval at long context, or a fixed human review rubric. Include uncertainty and failure examples.

Measure the actual system

Record peak memory, time to first token, inter-token latency, and aggregate throughput at your intended concurrency. State the checkpoint format, runtime, kernel, and hardware.

06Choose the next experiment

Weights dominate memory

Compare a supported 4-bit weight recipe with the 16-bit baseline. Check measured latency and held-out task quality; compression alone does not predict either.

KV cache dominates

Hold weight precision fixed, then compare 16-bit and 8-bit KV payloads in the calculator. Test long-context quality and cache-format support before lowering precision further.

Compute is the modeled limit

Compare W8A8 with weight-only formats, enabling the native-kernel assumption only as a what-if scenario. Verify actual kernel coverage and timings on the target device.

You need adaptation

QLoRA reduces memory for adapter fine-tuning; QAT adapts weights to a target quantization recipe. Choose based on what you intend to train and deploy, not a generic quality ranking.
